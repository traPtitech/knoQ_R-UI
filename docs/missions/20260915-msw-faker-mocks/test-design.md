## draft-eventの暫定HTTP契約を定める

以下はこのモック環境の契約であり，正式なバックエンドAPIの仕様ではない．URLは既存の`BASE_URL`を基準にする．生成済み`schema.d.ts`へ追記せず，既存のdraft-event型からfeature内で定義する．

| methodとpath                                     | 正常応答              | 入力・更新の要点                                                 |
| ------------------------------------------------ | --------------------- | ---------------------------------------------------------------- |
| `GET /draft-events`                              | 200，一覧             | 空の場合は`[]`．                                                 |
| `POST /draft-events`                             | 201，詳細             | `RequestDraftEvent`を受け，draft IDと候補IDを払い出す．          |
| `GET /draft-events/{id}`                         | 200，詳細             | 対象なしは404．                                                  |
| `DELETE /draft-events/{id}`                      | 204，bodyなし         | 関連回答も除く．対象なしは404．                                  |
| `POST /draft-events/{id}/confirm`                | 200，詳細             | `{ timeStart, timeEnd }`を受け，statusと確定日時を更新する．     |
| `GET /draft-events/{id}/availabilities`          | 200，回答一覧         | 回答0件は`[]`．対象なしは404．                                   |
| `GET /draft-events/{id}/availabilities/{userId}` | 200，回答または`null` | 存在するユーザーの未回答は`null`．draftまたはユーザーなしは404． |
| `PUT /draft-events/{id}/availabilities/{userId}` | 200，保存後の回答     | `RequestAvailability`を受け，同一ユーザーの回答を上書きする．    |
| `GET /users/{userId}/draft-availabilities`       | 200，回答一覧         | 対象ユーザーの全回答を取得する．ユーザーなしは404．              |
| `GET /draft-events/{id}/scheduling-results`      | 200，集計             | 対象なしは404．回答に基づいて計算する．                          |

不正なJSON，必須値の欠落，不正な日時や候補IDは400とし，draft-eventのエラーbodyは`{ message: string }`とする．日時は解釈可能なISO形式で開始より終了が後となることを確認する．回答の候補IDは対象draftに属するものに限り，同じIDを重複指定しても集計で二重計上しない．空の`slotIds`は回答済みだが参加可能な候補なし，と扱う．既存集計に合わせ，参加率の分母は回答者数，回答者0人なら参加率0とする．

HTTPエラーはcomposableの既存のerror状態へ伝え，更新失敗を成功として処理しない．通常APIは生成型のbody・statusに従う．本番認証・認可の再現は含めない．

## 画面確認をシナリオから再現する

- `default`: 固定ユーザー，所属グループ，利用可能な部屋を用意する．日程調整は募集中・締切済み・確定済み，回答済み・未回答，管理者・招待者を含む．日本語の長い名前も含める．
- `empty`: 日程調整・回答・イベントを空にし，ユーザーとグループは残す．空一覧から新規作成できることを確認する．
- `error`: 日程調整の一覧取得を500にする．ユーザー取得まで失敗させず，取得失敗の表示を再現する．ほかの404・400・500は個別テストのハンドラー上書きで確認する．
- `slow`: 対象APIに1秒の遅延を与える．画面の読込中と送信中を確認する．通常の自動テストでは遅延0とし，遅延テストだけ制御可能な待機を使う．

ブラウザではバックエンドを起動せず，開発モックで日程調整の一覧を直接開く．新規作成，回答の登録と変更，集計，管理画面での日時選択，通常イベント作成，イベント詳細と確定済みdraftの再取得まで確認する．部屋あり・なしの作成はテストデータをリセットして分ける．対象画面のアイコンも取得できることを確認する．

モック起動の設定は`npm run dev:mock`を入口とし，シナリオ，シード，基準日時を開発用設定で指定する案とする．ブラウザのデータリセットはリロードで行い，設定した初期データへ戻す．シナリオの切り替え時にはページを読み直し，古いキャッシュも持ち越さない．

通常起動は`npm run dev`，本番確認は`npm run build`と`npm run preview`で行う．本番のモジュール一覧にMSW，Faker，ハンドラー，シードデータがないことを確認する．公開ディレクトリからコピーされるworkerファイルの有無も記録し，配信ファイルの存在と実際のworker登録を分けて確認する．本番の環境変数だけでモックを有効化できないことも確かめる．

## テスト間の状態を持ち越さない

Nodeテストは開始時に`server.listen()`，各テスト後に`server.resetHandlers()`，終了時に`server.close()`を行う．これは[MSWのNode導入手順](https://mswjs.io/docs/integrations/node/)に沿う．ハンドラーのリセットだけでは自前のデータを戻せないため，データの再生成も明示的に行う．画面テストはコンポーネントのunmount，Piniaの作り直し，SWRVキャッシュの分離，時刻mockの解除を行う．

`useApiFetch`のHTTPエラー伝播に関する共通改修は，承認済みの範囲に追加しない．失敗表示の受け入れ検証は今回移行するdraft-eventを対象にし，通常APIの失敗はHTTPクライアントの応答として確認する．通常イベント作成後にdraft確定だけが失敗した場合は，イベントは作成済み，draftは未確定のままになることを確認する．自動ロールバックや再作成の機能は追加しない．

## 依存の互換性は一時環境で確認した

2026-09-15にnpmの公開情報を確認した導入候補はMSW `2.15.0`とFaker `10.6.0`である．Node `v24.12.0`とnpm `11.6.2`は両パッケージの対応範囲に入る．一時ディレクトリへの取得時は`--ignore-scripts`を指定した．

既存のTypeScriptコンパイラで`msw`，`msw/browser`，`msw/node`，`fakerJA`のimportを型検査し，現在と同じ`moduleResolution: node`で成功した．Node上の`fetch`をMSWで処理し，Fakerのシードと基準日時を指定した再生成が一致することも確認した．プロジェクト全体の互換性やブラウザ動作の証拠は，本実装後に取得する．

## 承認後は共有基盤を先に整え，2担当へ分ける

この分担も承認済みである．[parallel-feature-development](../../../skills/parallel-feature-development/SKILL.md)に沿い，共有基盤を調整役が先に実装・検証・commitする．その後，以下の2担当を分離したGit worktreeで起動する．

| 担当          | 所有するファイルと成果                                                                                                                                                 | 検証                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 調整役        | `package.json`，lockfile，Vite・TypeScript設定，`src/main.ts`，`src/mocks/`，共有型と生成・リセットの入口，文書，統合テスト．                                          | P1・P2・P4・P5・P6と統合後の全検証．                                 |
| `draft-api`   | `src/features/draft-event/`，`CreateDraftEvent.vue`，`DraftEventList.vue`，`DraftEventDetail.vue`，`DraftEventManage.vue`，`CreateEvent.vue`，`draftMockApi.spec.ts`． | P3，HTTPエラー伝播，型検査と担当範囲のlint．                         |
| `related-api` | user・group・room・eventの各feature配下の`mocks/`，`relatedMockApi.spec.ts`．                                                                                          | 8種類の通常API，生成型，一覧と詳細の整合性，担当範囲のlint・型検査． |

共有基盤ではシード・基準日時の渡し方，メモリ状態の型，関連ID，ハンドラーの受け渡しを定める．その共通commitをbase refとし，実SHAをHandoffへ記録する．依存順は「共有基盤→2担当の並行実装→related-api→draft-apiの順で統合→画面・全体検証」とする．

worktreeはリポジトリ内の`.agent-worktrees/<run-id>/{draft-api,related-api,integration}`，branchは`agent/<run-id>/<task>`とする．`run-id`は承認後の作成日時から決める．各worktreeは`npm ci`で依存を用意し，`node_modules`や`.env`を共有・複製しない．必要な画面確認のportは担当ごとに分け，8081，8082，統合後8083を候補に空きを確認する．

各担当のcommitを調整役がレビューしてintegrationへcherry-pickする．統合後にlint，型検査，全テスト，build，ブラウザ確認を行う．現在のmissionブランチを含む別ブランチへのmerge，push，PR作成，worktree削除はこの承認には含めない．

## 完了時に検証対象と結果を残す

統合後の同じcommitで，次を実行する．VitestはJSON reporterとV8 coverageを有効にし，成果物を`merge-rationale.md`から参照する．画面確認にはURL，シナリオ，シード，基準日時，ブラウザ，確認結果を添える．実行できなかった確認は省略理由と影響を記録する．

- `npm run lint`
- `npm run type-check`
- `npm exec -- vitest run --coverage.enabled=true --reporter=default --reporter=json --outputFile.json=<証拠ディレクトリ>/vitest.json`
- `npm run build`
- 対象文書のPrettier検査と`git diff --check`
